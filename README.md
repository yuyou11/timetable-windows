# 时间规划表 · 电脑版

和手机版配套的桌面程序。**数据格式完全通用** —— 手机导出的文件能导进电脑，反之亦然。

- **可执行文件**：`dist\时间规划表\时间规划表.exe`（文件夹版，**不需要装 Python**）
  —— exe 不能单独拿出来，必须和同目录的 `_internal` 一起
- **界面**：HTML/CSS/JS（就是你正在学的那套）
- **后端**：Python 3.14（只用到标准库 + pywebview）
- **数据位置**：`%APPDATA%\Timetable\data.json`

---

## 一、怎么用

双击 `dist\时间规划表.exe` 就能开。

**发给同学**：直接把这个 exe 发过去（微信、QQ、U 盘都行），对方双击就能用，
**不需要装 Python，也不需要装任何东西**。

> 系统要求：Windows 10 1803 以上 / Windows 11。
> 依赖系统自带的 Edge WebView2 运行时（Win11 和较新的 Win10 都自带）。
> 如果对方打开是白屏，让他装一下 [WebView2 运行时](https://developer.microsoft.com/microsoft-edge/webview2/) 就行。

### 六个页面

| 页面 | 干什么 |
|---|---|
| **今天** | 此刻在做什么、还剩多久、明天的预告（含起床时间）、今日时间线 |
| **课表** | 一周的课程网格，可以翻周 |
| **课程编辑** | 图形化增删改课程，不用手写 JSON |
| **作息编辑** | 图形化改六套作息模板，含「一键改起床时间」 |
| **导入导出** | 和手机版交换数据，或用 AI 提示词生成数据 |
| **设置** | 学期名称/起始日/总周数、课前提醒、悬浮窗开关 |

### 桌面悬浮窗

在设置里打开后，桌面右下角会出现一块小卡片：

```
┌────────────────────────────────┐         ┌──┐
│ ● 前往教室            还剩 2 分 │         │  │
│   接着 14:00 第 5-6 节 · 无课   │   ⇄    │◀ │   ← 拖到边缘就缩成这样
│   [打开主窗口]  [关闭]          │         │  │
└────────────────────────────────┘         └──┘
      自由浮动 / 悬停时                     贴边收起
```

- **拖** 到任意位置（按住卡片空白处）
- **单击** 卡片 → 打开主窗口
- 「打开主窗口」/「关闭」两个按钮随时可点

**「关闭」是把悬浮窗彻底关掉**（连设置里的开关一起关），
重启程序不会自己回来。想再打开：主窗口「设置」页的开关，或托盘菜单。

> 注意它和「贴边收起」不是一回事 —— 那个只是缩成小方块，移到边上还会自己弹出来。

#### 系统托盘图标

程序启动后，右下角托盘区会有一个图标。**这是永远都在的入口** ——
不管悬浮窗被隐藏、还是主窗口被关掉，右键点它都能叫回来：

```
┌──────────────────┐
│ 打开主窗口        │
│ 显示悬浮窗      ✓ │
│ ──────────────── │
│ 退出             │
└──────────────────┘
```

为什么需要它：**先隐藏悬浮窗、再关掉主窗口**，程序其实还在后台跑，
但那时候没有任何入口能把它叫回来（只能在任务管理器里看到进程）。
托盘就是修这个的。

托盘起不来（缺库、被安全软件拦）不影响使用，只是少了个兜底入口。

#### 贴边自动隐藏

**把卡片拖到屏幕边缘松手，它会缩成一个小方块，只留一个箭头在外面。**
鼠标移上去自动滑出来，移开又缩回去 —— 平时完全不占地方。

四个边都支持，箭头指向"拉出来的方向"。位置和停靠状态会记住，下次打开还在那。

想取消：把卡片从边缘拖回屏幕中间就行。

关掉主窗口时，如果悬浮窗或托盘还在，程序会留在后台继续跑（这正是它们的意义）；
都没有的话，关掉主窗口就是真的退出了。

**拖不出去**：拖动时窗口会被限制在屏幕内。贴到边缘就停住，再往那个方向拖不动 ——
免得一不小心把卡片推到屏幕外面，只剩任务栏里一个按钮，看着像程序坏了。

> **为什么是卡片不是圆球**：第一版做的是圆球 + 鼠标悬停展开面板，
> 结果发现**鼠标一从球上移开，面板就收了，根本点不到按钮**
> （鼠标从球移到面板要经过一段"缝隙"，hover 会断开）。
> 而且透明窗口在 WebView2 上不生效，会露出一个突兀的黑白方框。
>
> 改成常驻小卡片之后：不依赖悬停、不依赖透明，按钮一直在。
> **能用比好看重要** —— 尤其是一个要天天看着的东西。

> **贴边隐藏的几何计算单独放在 `app/dock.py`，配了一组单元测试。**
> 为什么不放在 JS 里？因为「贴哪个边、放哪、多大」是纯数学，
> 放 Python 里能测；放 JS 里就只能靠眼睛看了。
> JS 只负责"感知"（鼠标进出、拖了多少、松手了），
> Python 负责"判断"。这个分工在 `ball.js` 顶部也写了。

#### 圆角

卡片和小方块都是**四个角全圆角**，和系统其他窗口一致。

窗口的圆角是 Windows 自己裁的（`app/winutil.py` 的 `set_rounded_corners`），
页面里那圈 1px 边框的圆角是 CSS 画的（`ball.html` 的 `--radius-card`）。
**两边的半径必须相等**，否则边角处会看到边框被切掉一截 ——
`tests/test_dock.py` 里有一条测试直接读 `ball.html` 来核对。

> **为什么不用 `SetWindowRgn` 自己裁一个圆角**：那种做法半径想多大就多大，
> 但**没有抗锯齿**（边缘一圈锯齿），而且**尺寸一变就得重画**
> —— 悬浮窗在悬停时要在 244×104 和 26×76 之间来回变，忘了重设圆角就错位。
>
> 交给 DWM 则两者都没有。代价是半径由系统定（实测约 10 逻辑像素，
> 正好和卡片的 CSS 半径一致），不能自由调。

> **⭐ 一个藏得很深的坑：`disable_shadow()` 会把圆角一起关掉。**
>
> `DWMWA_NCRENDERING_POLICY = DWMNCRP_DISABLED` 关掉的是**整个非客户区
> 渲染**，而 Win11 的自动圆角正属于非客户区渲染。
>
> 所以现象是：**Win11 本来默认就给无边框窗口加圆角，我们一关阴影就把它弄没了。**
> 修复就是关完阴影之后补一次 `set_rounded_corners(..., True)`，
> 两件事可以同时成立。
>
> 这个坑值得记，是因为它特别反直觉：代码里没有任何一行在"设置直角"，
> CSS 里 `border-radius` 也明明写着 —— 可窗口就是方的。
> 因为 CSS 的 `border-radius` 只是**画在页面里的一个圆角线框**，
> 真正把窗口裁成圆角的是 DWM，两件事完全独立。
>
> 排查方法见 `tools/exp_corner.py`：给窗口铺满纯红、衬在深色底上，
> 做一组**带对照**的矩阵（什么都不做 / 只关阴影 / 关阴影+要圆角 / 只要直角），
> 再读四角像素看哪些被裁掉了。有对照组的实验才能定位到是哪一次调用干的。
>
> ⚠️ 这条路走过一次弯路：为了让贴边那一侧保持直角，用 `SetWindowRgn` 拼过
> 一个"左圆右方"的形状。后来发现**四个角都圆就行**，于是整套区域代码都拆了。
> 教训是**先问需求有多复杂，再选实现手段** —— 逐角控制是区域唯一的优势，
> 一旦不需要它，区域就只剩缺点了。

## 二、改数据：两种方式

### 方式一：图形界面（推荐）

- **课程** → 「课程编辑」页，点「添加课程」/「编辑」/「删除」
- **作息** → 「作息编辑」页，选日型 → 改格子；改起床时间用「改起床时间」按钮

改完立刻生效，悬浮窗和今天页会跟着变。**不用懂 JSON。**

### 方式二：直接改 JSON

「导入导出」页可以导出文件，用记事本或 VS Code 改完再导入。
格式标准和手机版一样，见手机版仓库的 `docs/数据格式标准.md`
（本地开发时两个项目是同级目录）。

**更适合"从零开始"的做法**：用「导入导出」页里的 AI 提示词。
提示词里已经填好了你当前的学期信息，复制给豆包 / DeepSeek / Kimi，
再把课表截图发过去，它就会输出能直接导入的 JSON。

## 三、开发

```powershell
# 直接运行（改完代码立刻能试）
python -m app.main

# 跑单元测试（不需要界面）
python -m unittest discover -s tests

# 跑冒烟测试（接口层面）
python tests/smoke.py

# 重新生成图标（改了 tools/icon-source.png 之后）
python tools/gen_icon.py

# 打包成 exe（打包前先关掉正在运行的旧版本，否则文件被占用）
python build.py                  # 文件夹版（默认，日常自用推荐）
python build.py --onefile        # 单文件（要发给同学时用这个）
python build.py --console        # 带控制台，调试用（能看到报错）
```

> **默认是文件夹版**（`dist/时间规划表/`）。选它的理由：启动不用每次解压
> （单文件版每次开机都要把整个包解压到 `%TEMP%\_MEIxxxx`），而且**只有一个进程**
> —— 单文件版是"引导进程 + 应用进程"，任务管理器里会出现两个同名进程，
> 容易让人以为开重了。
>
> 代价是**exe 不能单独拿出来**，必须和同目录的 `_internal` 一起。
> 要发给同学就 `--onefile`，或者把整个文件夹压缩成 zip。
>
> 两种产物可以并存（`build.py` 只清理本次要生成的那一个）。
> `--onedir` 这个旧写法仍然认，行为不变。

> 这里不写测试的具体条数 —— 写了必然过期。跑一下就知道。

改前端时不用重新打包 —— `python -m app.main` 直接用磁盘上的 HTML/CSS/JS。

### 目录结构

```

├── slots.py          第 1-10 节的时间表
├── engine.py         时间轴引擎（两层叠加 + 收口）
├── day_type_policy.py 日型策略（启用哪几种日型）
├── format_spec.py    数据格式标准 v3 的解析与生成
├── builtin_data.py   内置数据（自动生成，勿手改）
├── ai_prompt.py      AI 提示词
├── store.py          本地存储（JSON 文件）
├── tray.py           系统托盘图标
├── winutil.py        Win32 小工具（工具窗口、圆角、关阴影）
├── screen.py         屏幕 / DPI / 系统主题 / 资源路径
├── assets/           应用图标（自动生成，勿手改）

└── web/              界面
    ├── index.html    主窗口

    ├── app.js

tests/                单元测试 + 冒烟测试
tools/                工具脚本（生成内置数据、生成图标、诊断）
```

> `screen.py` 里那几个函数原来住在 `main.py`。搬出来是为了能单测 ——
> 它们要么是纯函数、要么只读系统，本来就不需要开窗口。
>
> ⚠️ **`main.py` 顶部有一行从 `screen.py` 的再导出，不要删。**
> `tools/exp_dock.py` / `exp_windows.py` / `diag_web.py` 和 `run.py` 都是
> `from app.main import ...` 的写法，删了它们全部 ImportError ——
> 而这些是排查窗口问题的诊断工具，平时不跑，坏了一直不会有人发现。
>
> 那一行必须是**显式名字列表**，不能改成 `from .screen import *`：
> 星号导入会跳过下划线开头的名字，`_bg_color` 会静默消失，
> 而它正是 `exp_dock.py` 要的。`tests/test_main_helpers.py` 盯着这两条。

> `tests/test_api_contract.py` 值得单独说一句：它扫前端源码里所有
> `call('方法名')`，逐个断言 `Api` 上真的存在这个方法。
>
> 因为**前后端之间没有任何编译期检查** —— 名字写错，运行时既不报错也不崩溃，
> 只是那次调用静默失效。这个项目已经因此吃过一次：`app.js` 一直在调
> `mark_launched`，而 `Api` 上从来没有这个方法（它只在 `Store` 上，被
> `_serializable = False` 挡在桥外），后果是首次启动走完向导弹一个「出错了」。

### 内置数据是生成的，不要手改

`app/builtin_data.py` 由 `tools/gen_builtin.py` 从**手机版真实导出的
`example-full.json`** 转换而来。

这样两边永远一致 —— 手抄六套模板（100 多格）必然出错，而且改了手机版就对不上。
要更新内置数据：先在手机版改，导出，再跑一次生成脚本。

### 图标也是生成的，不要手改

`app/assets/` 下的两个文件由 `tools/gen_icon.py` 从素材
`tools/icon-source.png` 生成。换图标就换那张素材，再跑一次脚本。

脚本要做三件事，都是**素材本身不能直接用**的原因：

  1. **居中** —— 素材的图案不在画布正中（左右留白差 13px），
     直接当图标用，标题栏和托盘里肉眼看得出是歪的
  2. **清透明边** —— 素材四角的 alpha 是 3 而不是 0，缩放后会变成脏边
  3. **生成多尺寸 .ico** —— Windows 在任务栏用 32、Alt+Tab 用 48、
     大图标视图用 256，只塞一张的话系统只能自己缩，比预缩的差

改完记得重新打包 —— 而且要重新打包**两次生效**：图标既要在运行时
读（`--add-data`），又要编译进 exe（`--icon`），见下面第 8 条。

## 四、踩过的坑（改代码前值得读）

这些坑都是实际踩出来的，有些花了大半天才定位到。

### 1. 无边框窗口会让程序硬崩（最坑的一个）

**症状**：主窗口好好的，一加上悬浮窗（无边框窗口），程序跑十几秒后
以 `0xC0000409` 直接死掉，**日志里一个字都没有**。

**原因**：pywebview 创建窗口时会**递归遍历 `js_api` 对象的所有公开属性**，
找出要暴露给 JavaScript 的方法（见 `webview/util.py` 的 `get_functions`）。
如果 `js_api` 上存了 pywebview 的 `Window` 对象，它就会钻进
`.native.AccessibilityObject` —— 而**无边框窗口的这条属性链是无限的**：

```
window.native.AccessibilityObject.Handle.Zero.Zero.Zero.Zero...  ← 无限
```

递归深度爆掉，C 栈撑破，进程硬崩。

**解决**：把这类属性改成下划线开头（`self._window`），
扫描器会跳过下划线开头的属性。
另外 `Store` 类上加了 `_serializable = False`，同样是为了让扫描器别往里走。

**这个坑的教训**：库的「自动发现」机制（这里是自动暴露 API）会遍历你的对象图。
**凡是把框架自己的对象存到自己身上，都要小心被它扫到。**

### 2. `--windowed` 打包后静默死亡

窗口模式下 `sys.stdout` / `sys.stderr` 是 `None`。任何一次 `print()`
都会抛异常，而因为没有控制台，你什么都看不到。

**解决**：`run.py` 里在程序最开始就把它们接管掉，并把崩溃写进
`crash.log`。

### 3. `--exclude-module` 排太狠会切断传递依赖

我为了减小体积排除了 `http.server`，结果 pywebview 内部的
`wsgiref.simple_server` 依赖它 —— **打包过程完全成功，没有任何警告**，
一运行就崩。

**只排确定没人依赖的叶子模块**（tkinter、PIL、numpy 这类）。

### 4. `background_color` 只接受 6 位十六进制

写 `#00000000`（8 位带透明度）会直接抛
`is not a valid hex triplet color`，程序起不来。

### 4.5 透明窗口在 WebView2 上不生效

窗口设了 `transparent=True`，但 WebView2 在部分环境下**不会把页面背景
真正渲染成透明** —— 屏幕上出现一个突兀的黑白方框（用户截图里看得很清楚）。

**解决**：不再依赖透明。窗口改成不透明，底色跟随系统主题
（`is_dark_mode()` 读注册表判断），页面自己画一个带边框的卡片。
这样不管透明生效不生效，看起来都是一整块。

### 4.10 在窗口自己的关闭事件里销毁它自己 = 无限递归

**症状**（用户报的，附了完整的 Windows 崩溃框）：

```
System.InsufficientExecutionStackException: 堆栈空间不足
   在 System.Windows.Forms.Form.OnFormClosing
```

**触发条件很具体**：先关掉悬浮窗，再关主窗口。

**原因**：`_on_main_closing` 里「真的退出」那个分支调了 `_quit()`，
而 `_quit()` 会销毁**所有**窗口 —— 包括正在关闭的主窗口自己。

```
关闭主窗口 → FormClosing → _quit() → destroy(主窗口) → FormClosing → _quit() → ...
```

无限递归，直到把调用栈撑爆。

悬浮窗开着时走的是 `hide()` 分支，不碰 `_quit()`，所以**不会崩** ——
这也正是它藏了这么久的原因：绝大多数时候你都是开着悬浮窗用的。

**修法**：`_shutdown(keep=...)` 接受一个「不要销毁的窗口」，
从关闭事件里触发时把当前窗口传进去；再加一个 `_shutting_down` 标志防重入。

> **规矩：永远不要在窗口自己的关闭事件里销毁它自己。**

### 4.11 托盘回调里抛异常会静默杀死消息循环

pystray 的菜单回调跑在它自己的消息循环线程里。回调里抛一个未捕获的异常，
**消息循环就停了** —— 图标还留在托盘上，但从此点它没有任何反应。

这种「看着还在、实际已死」比干脆消失更让人困惑。所以 `tray.py` 里
所有回调都包在 `_safe()` 里，一律兜住。

### 4.12 悬浮提示窗口应该设成「工具窗口」

默认情况下，无边框窗口**也会出现在任务栏里** —— 一个悬浮提示占着任务栏按钮，
很不合理（用户也提了这点）。

给窗口加 `WS_EX_TOOLWINDOW` 扩展样式、并清掉 `WS_EX_APPWINDOW` 就能解决：

```python
style = GetWindowLongPtrW(hwnd, GWL_EXSTYLE)
style = (style | WS_EX_TOOLWINDOW) & ~WS_EX_APPWINDOW
SetWindowLongPtrW(hwnd, GWL_EXSTYLE, style)
ShowWindow(hwnd, SW_HIDE); ShowWindow(hwnd, SW_SHOW)   # 必须刷新一次
```

最后那两行不能省 —— 只改样式的话任务栏按钮会一直留着，直到窗口重建。

顺带一并关掉了**系统给无边框窗口自动加的阴影**（用户反馈太深）。
那个阴影只能开或关，改不了浓淡，所以关掉，靠 1px 边框给卡片定形。

### 4.13 找窗口句柄不能碰 `window.native`

要拿 HWND 去做上面那些调整，最直接的路是 `window.native.Handle`。
但**访问 `.native` 有风险** —— pywebview 建窗口时会递归遍历对象图，
碰到它自己的原生对象可能无限递归（见 4.1）。

所以这里绕开，用 `FindWindowW(None, 标题)` 按标题找。
代价是**三个窗口的标题必须互不相同**，否则会找错 ——
这一点在 `winutil.py` 里用常量写死了并加了注释。

（顺带：这个 bug 和 4.1 是**同一个根因的两种表现** ——
都是「pywebview 会遍历你的对象图」惹出来的。）

### 4.7 DPI 缩放：同一个 API 在程序启动前后返回不同的值（最阴的一个）

**症状**：贴边隐藏做完了，**贴着上边能停靠，贴着右边不能**。
四个边里只有上边好使，听起来像几何算错了，但公式明明是对的。

**根因**：Windows 会把非 DPI 感知的进程「虚拟化」——
系统 API 返回按缩放比例缩小的**逻辑值**。而 **WebView2 一初始化
就会把进程变成 DPI 感知**。于是同一个
`SystemParametersInfoW(SPI_GETWORKAREA)`：

```
程序启动时        → 2048×1232   （125% 缩放下的虚拟值）
webview 起来之后  → 2560×1540   （真实物理像素）
```

**而窗口坐标一直是物理像素。** 用早期那个 2048 当右边界算「贴右边了吗」，
窗口明明贴着屏幕右缘（x=2312，离真实右缘 4px），算出来却离了 560 像素。

**为什么只有上边好使**：上边缘在两种单位下都是 0，碰巧对得上。
右边缘一个 2048 一个 2560，差了一整块。

**第一步的解决**：在 `run.py` 里、**任何窗口创建之前**声明 DPI 感知：

```python
ctypes.windll.shcore.SetProcessDpiAwareness(2)   # PER_MONITOR_DPI_AWARE
```

这样所有 API 从始至终都在同一个坐标系里。

### 4.7b 但真正的原因比这个更深：**不要自己乘缩放系数**

上一步做完，我以为「现在一切都是物理像素了，所以界面尺寸要乘缩放系数补回来」，
于是把窗口尺寸和坐标都乘了 1.25。

**结果悬浮窗直接跑到屏幕外面去了**（用户报的「一打开软件就不出现悬浮窗」）。

实测数据：

```
我想要：x=2241  宽 305
实际是：x=2795  宽 381      2241×1.25 = 2801 ≈ 2795
                            305 ×1.25 = 381  = 381
```

**尺寸和位置都被乘了一次 1.25 —— 双重缩放。**

去翻 pywebview 的源码才明白：

```
198: # Store initial window size as logical pixels, will be converted later
435: # Convert physical pixel dimensions to logical pixels for the API
621: # Input x/y are in logical pixels, need to convert to physical
```

**pywebview 的 Windows 后端整个公开 API 都是逻辑像素，DPI 换算它自己在内部做。**
`create_window` / `move` / `resize` 收的是逻辑值，`window.x/.y/.width/.height`
返回的也是逻辑值。调用方**一个缩放系数都不该乘**。

所以正确做法是：

| 层 | 用什么单位 |
|---|---|
| 我们自己的全部计算（dock.py、Store 里的位置） | **逻辑像素** |
| 交给 pywebview 的值 | **逻辑像素**（原样传，不乘） |
| 从 Win32 直接拿的 `SPI_GETWORKAREA` | 物理像素 → **除一次**转成逻辑 |

`ui_scale()` 因此**只有一个用途**：把 Win32 的工作区换算成逻辑像素。
其他地方用到它都是错的。

> **排查过程值得记下来**（我全程看不见屏幕）：
>
> 1. 猜不出来，就写了个**外部检查工具** —— 从进程外面用 `EnumWindows`
>    列出所有相关窗口，报告每个窗口的**真实位置、尺寸、可见性**。
>    一跑就看到了 `(2795,1740)` 而工作区只到 `(2560,1540)`。
> 2. 拿实测值反推：2795/2241 = 1.247、381/305 = 1.249 —— 都约等于屏幕缩放 1.25。
>    **数字自己把答案说出来了。**
> 3. 再去翻源码确认机制，然后改。
>
> 两个可复用的点：
> **① 看不见的现象，就把它变成能读出来的数字**（位置、尺寸、标志位）。
> **② 用「我想要的」和「实际得到的」做除法** —— 比值往往一眼就指向原因。

### 4.7c 顺手发现的第二个 bug：刷新任务栏时把隐藏窗口显示了

`make_tool_window()` 为了刷新任务栏，要「隐藏再显示」一次。
我一开始写成无脑的 `SW_HIDE` 然后 `SW_SHOW` ——

**结果把 `hidden=True` 创建的提醒提示条也显示出来了**，一开机就杵在屏幕上。

修法：先记下原本可不可见，刷完恢复原状。

这也是检查工具发现的 —— 它不只查位置，也查可见性。

### 4.7d 不要回读窗口位置

pywebview 的 `window.x/.y` 在**创建窗口后的短时间内不可靠**：
实测同一份代码跑两次，读回来的位置一次对一次错。窗口还没摆好就去读，
拿到的是 WinForms 的默认位置，然后这个错值又被当成真值用来算下一步。

所以：**我们自己算出来的位置才是唯一真相**，窗口只是被我们摆过去而已。
代码里用 `self._ball_x/_ball_y` 记位置，`self._ball_w/_ball_h` 记尺寸，
一律不回读。这和「**不要让外部状态当你的真相来源**」是同一个原则。

### 4.7e 换成「自己记状态」之后，漏改一处读取点 = 静默跑偏

改成 `self._ball_x/_ball_y` 之后，我在 `_create_ball` 里**只赋了尺寸、忘了赋位置**。
于是 `_polish` 稍后调用 `_apply_ball_geometry` 时读到的位置是初始值 `(0,0)`，
**把已经摆好的悬浮窗又挪到了屏幕左上角**。

表现是「一打开软件悬浮窗不见了」—— 其实它贴在左上角，存在感极低。

这个 bug 有三个特点，都值得警惕：

1. **不报错**。读一个值为 0 的属性完全合法，没有任何异常。
2. **开发模式看不出来**（那时的代码路径不同），只有打包后才稳定复现。
3. **我加的调试日志恰好打在另一个函数里**，打出来的是"应用之后"的值，
   反而误导了我一轮。

> 教训：**把一个状态从「回读外部」改成「自己维护」时，
> 要把这个状态的所有读取点列出来，逐个改。** 漏一个，它就读到初始值。
>
> 具体做法：改完立刻 `grep` 一遍这个变量名，看每一处是不是都符合预期。
> 我就是靠 grep 才确认 `_ball_x/_ball_y` 的 7 个读写点全部正确的。

### 4.8 pywebview 的 min_size 默认是 (200, 100)

想 `resize(24, 72)` 缩成一条边，结果窗口纹丝不动，量出来还是 200×100。

`create_window` 的 `min_size` 默认值卡住了。要缩到 200 以下，
建窗口时就得传 `min_size=(26, 26)`。

### 4.9 不要吞异常

`_apply_ball_geometry` 里本来写的是：

```python
try:
    self.ball.resize(w, h); self.ball.move(x, y)
except Exception:
    pass          # ← 这一句让「拖到右边不缩回去」查了半天毫无线索
```

改成写进日志之后，一跑就知道是哪一步的问题了。
**吞异常和静默失败是同一类错误，代价是排查时间。**

### 4.6 悬停展开的面板永远点不到

第一版悬浮窗用纯 CSS 实现展开：

```css
#ball:hover + #panel { opacity: 1; }   /* ← 写起来简洁，用起来灾难 */
```

问题是鼠标从球移到旁边的面板时，中间要经过一段"缝隙"——
此刻既不在球上也不在面板上，hover 断开，**面板在你手还没到之前就收了**。

**解决**：不靠 hover。要么用点击切换（JS 控制 class），
要么干脆把内容常驻显示。这里选了后者。

> 教训：**凡是需要鼠标"跨过一段距离才能到达"的悬停交互，都要当心这个缝隙。**
> CSS 的 `:hover` 只认"当前指针在哪"，不认"你正打算去哪"。

### 5. 前端「静默不执行」

如果 `app.js` 有语法错误，整个文件都不会执行 —— **包括你自己写的
`window.onerror`**。于是窗口开着、什么都不做、也没有任何报错。

**解决**：`window.pywebview` 可能已经就绪，也可能是之后才就绪，
两条路都要接上（见 `app.js` 末尾）；同时把 JS 报错转发给 Python 写进日志。

### 6. 改起床时间会「死锁」

作息模板里「睡觉」和「起床、洗漱」是相邻两格。想改起床时间，
一格一格改会互相报重叠 —— **每一步都被拦下，每句报错听起来都对，但就是改不动**。

**解决**：`shift_wake_time()` 一次改两格，整段平移到下一个「锚点」为止。
锚点 = 课表格子（它的时间由学校课表决定，不能挪）。

> **凡是「用户必须按特定顺序做几件事」的地方，都值得做成一个动作。**

### 7. 模板存了但读不回来（手机版也中过这个）

存模板和读模板共用了同一段写出逻辑，那段会输出 `"templates": {...}`
（带键名的片段）。问题是 **`"templates": {...}` 不是合法 JSON** ——
一个裸的键值对，没有外层大括号。

存进去之后解析直接失败，然后被「坏了就当没有」的兜底吞掉，
**用户改的模板静默消失**，一点报错都没有。

**解决**：写出逻辑加 `withKey` 参数，存本地存储时输出完整对象。
两边都补了「存进去再读出来」的往返测试。

### 8. `--icon` 和 `--add-data` 是两件事，漏一个图标就不对

打包时这两个都写了才对：

```python
"--add-data", f"{ROOT / 'app' / 'assets'}{SEP}assets",   # 运行时资源
"--icon",     str(ROOT / "app" / "assets" / "icon.ico"),  # 编译进 exe
```

它们管的是**不同地方**的图标：

| 参数 | 管哪儿 |
|---|---|
| `--icon` | exe 文件在资源管理器里显示的那个（编译进 PE 头） |
| `--add-data` | 窗口标题栏左上角那个（运行时由 `webview.start(icon=...)` 读） |

漏掉 `--add-data` 尤其隐蔽：程序照跑、界面照显示，**只是图标静默变回
Windows 的默认图标**，没有任何报错。

同理，`main.py` 里取图标路径必须走 `resource_path()` 而不是 `__file__` ——
打包后资源在 `sys._MEIPASS` 的临时目录里，`__file__` 拼出来是找不到的。

> 顺带一个反直觉的点：`webview.start(icon=...)` 的 `icon` 参数是**全局**的，
> 管所有窗口，不是给单个窗口设的。

### 9. 长期存在的窗口 + 按钮自我禁用 = 「再也点不动了」

悬浮窗上的「关闭」按钮点一次会禁用自己（防连点）。

问题在于：**悬浮窗是长期存在的窗口**，关掉只是 `hide()`，页面并没有销毁。
所以用户在主窗口设置里把它重新打开时，那个禁用状态**还在** ——
表现是「悬浮窗关不掉了」，而且没有任何报错，**只是点了没反应**。

**解决**：加一个 `window.ballShown()`，在所有会让悬浮窗重新出现的
路径上调用一次，把按钮恢复成可用。

这类 bug 的真正风险是**漏掉某个调用点**（设置页、托盘菜单、以后新加的入口），
所以测试盯的是「哪些路径调了恢复」，而不是按钮长什么样。

**教训**：凡是「前端会自己禁用某个控件」+「页面不会被销毁重建」的组合，
都要问一句 —— **什么事件能把它恢复回来？** 想不出来就是漏了。

## 五、为什么是 Python + pywebview

选它不是因为最好，而是因为**最适合你**：

| 你可能的技术 | 界面用什么写 | 要不要装大工具链 | 你自己能不能改 |
|---|---|---|---|
| **Python + pywebview** | **HTML/CSS/JS** | 不用（Python 你已有） | ✅ 前端和 Python 都在你射程内 |
| Electron | HTML/CSS/JS | 要装 Node | 能改前端，但打包体积 150MB+ |
| Tauri | HTML/CSS/JS | 要 Rust + MSVC（约 3–4 GB） | 前端能改，后端是 Rust |
| C# WPF | XAML | 要 .NET SDK | 要重学一门 |

对「你要能看懂、能自己改」这个目标，pywebview 是唯一一个前后端都在你能力圈内的选项。
代价是 pywebview 不如 Electron 成熟，上面那些坑就是这么来的 —— 但坑都填好了，
写在这份 README 和代码注释里。
